# コンテンツ品質ルール（時制・断定）

制定: 2026-08-07 ／ 対象: `src/` 配下の全記事ページおよび `src/data/articles.ts` の description

本番確認で「時間経過により誤りになる表現」が検出されたことを受けて明文化する。
公開済みコンテンツは書いた瞬間が正しくても、放置すれば誤情報に変わる。**書いた時点で正しい**ではなく**放置しても誤りにならない**書き方を標準とする。

## 時制

- **相対時間表現（残り約◯週間／残り約◯日／締切間近／まもなく／今週中／あと◯日）は本文に書かない。**
  これらは公開直後から劣化し、数週間で確実に誤情報になる。
- **期限は絶対日付で書く。** 「令和8年8月14日」「2026年7月24日」のように、読んだ日がいつでも解釈が変わらない形にする。
- **受付状況には必ず「◯年◯月◯日時点」を添える。**
  「受付中」「公募中」を裸で書かない。「2026年8月7日時点で受付中」と書けば、時間が経っても
  「その時点の情報」として読者が古さを判断でき、誤情報にはならない。
- **残数・残枠・執行率は、公表値がある場合のみ、公表日を添えて記載する。**
  例: 「残り受付目安約20件（2026年7月15日時点）」。
  公表されていない場合は推測で埋めず「公表されていないため公式で要確認」と書く。

### 例外（相対表現でも可）

読者が読んだ時点を基準とする**行動指示**は時間劣化しないため対象外。
例:「今週中に2〜3社へ見積依頼を出す」「更新後まもなく解約を希望している」。
また「残り約90%は長期契約」のような**比率**は時間表現ではないため対象外。

## 断定

- **結果を約束する表現（確実に◯◯できる／ほぼ確実に回収可能／必ず採択される）は使わない。**
  蓋然表現（◯◯しやすい／◯◯できる見込み／◯◯になりやすい）にする。
  補助金は先着・審査・予算制約があり、投資回収は前提条件で変動するため、約束はできない。
- **公表されていない終了・再開は断定しない。**
  「終了した」と書けるのは、公表された受付期間が満了した事実まで。
  制度そのものの廃止や再公募の有無は、公表がなければ「確認できていない」と書く。
- **予算残額・執行率を推測しない。** 公表がなければ「確認できない」と明記する。

### 例外（断定表現を残す箇所）

- **悪質勧誘の例示**（例:「高利回りで確実に儲かると勧誘された」）は、断定表現そのものが
  注意喚起の対象であるため原文のまま残す。
- **読者への実務注意**（例:「要件の確認は補助を確実に受けるうえで欠かせません」
  「補助を確実に受けられるとは限りません」）は、結果の約束ではないため対象外。

## 検出（レビュー手順）

- **語尾の正規表現でスクリーニングしない。** 「確実に〜できます／されます」のような
  述語の語尾リストで検出すると、`ほぼ確実に回収可能（1.5〜2.5年）。` のような
  **体言止め＋句点**の文を取りこぼす。実際に #308 でこの取りこぼしが発生し、#309 で是正した。
- **正しい手順は「該当語を全件抽出 → 文脈を目視分類」。**
  検出すべき語: `確実` `必ず` `間違いなく` `残り約` `締切間近` `まもなく` `今週中` `あと◯日`。
  件数が多くても全件を出力させ、1件ずつ「結果の約束か／指示・条件・比率か」を判断する。
- **PRでは残存ゼロを機械確認して本文に記載する。**
  あわせて「変更禁止と判断して残した件数」も記載し、意図的に残したことを明示する。

## 同型テンプレートの判定統一（#320で確立）

- 同じ文型が複数ページで共有されている場合、箇所単位の出典有無だけで是正/維持を判定すると、サイト内で表現が割れる（17ページ是正済みのFAQテンプレが3ページだけ残る等）。読者には同じ主張が「最高水準」と「高水準」で割れて見え、是正前より悪い状態になる。
- 判定基準: 同型が他ページで既に是正済みなら、出典の有無にかかわらず是正する（サイト内の表現統一を箇所単位の出典判定より優先する）。
- 姉妹ページ間の非対称も同様に扱う（一方を是正したら他方も揃える）。

## 是正作業の実務則（#320で確立）

- 語だけを機械的に削ると助詞が壊れる（「〜で」を巻き込んだ削除による述語欠落など）。削除後の文が単独で成立することを必ず確認する。
- 数値を消すときは派生（算術で導いた金額・順位・超越表現）も同じ論理単位として追う。
- 過剰修正に注意: 順序尺度の表ラベル・1日の負荷曲線の最大値・範囲を限定する副詞（「世界的に縮小」等）は外部比較ではないため是正対象外。
- 抽出は1回で終わらない前提で設計する。言い換え族は「国内最大級→全国最高水準→全国で最も高い→全国1位→世界トップシェア」と連鎖するため、敵対的検証で族の取りこぼしを検出しながらラウンドを重ねる。

## 発注データの検証義務（#321で確立）

- 発注文のDATA_ACTUALであっても、リポジトリ内の検証済みデータと矛盾した場合は実装を止めて確認する。発注側の数値を無条件に優先しない。
- 特に前年同月比・前月比のような「既存データとの差分」は、リポジトリ側の値で機械再計算し、発注値と一致するかを確かめる。不一致なら実装側の再計算値を採用し、発注者へ出所確認を求める。
- 配列データから特定の月・年の値を取り出すときは、位置（インデックス）で推定しない。月ラベル定義（MONTH_LABELS）と列定義（columnIndex）を確認してから抽出する。フィルタを噛ませた配列の位置は元データの位置と一致しない。

## 月次データ繰上げ時のチェック（#321で確立）

- カードの値を新しい月へ繰り上げるときは、値だけでなく見出し用の month フィールド・「◯月分」表記・出典の公表日を同時に更新する（値と月表記の不整合が最も起きやすい）。
- 賦課金加算例などの派生計算・検算式は、基準値の変更に追随して全演算子（＋－×÷）で機械照合する。
- 年別比較表の行と月の対応は、リポジトリ全数との機械照合で確認する（月ズレの誤修正を防ぐ）。

## 発注データ検証義務の適用範囲（#322で拡張）

- 検証義務はDATA_ACTUALの数値だけでなく、発注文の「背景」「バッチ共通の軸」「注意事項」といった要約・散文の記述にも適用する。要約は一次資料からの転記過程で条件が付加・混同されやすい。
- 制度の要件・前提条件（認証・診断・入会等）が共通軸で複数ページに展開される場合は、展開前に各ページのDATA_ACTUAL本体に該当記載があるかを1件ずつ照合する。共通軸にあってDATA_ACTUAL本体にない条件は書かない。
- 実例: #321は前年同月値（配列インデックスからの推定ミス）、#322は「石川県=省エネ診断が前提」（調査要約からの転記ミス）。いずれも実装側の照合で公開前に阻止された。

## 「確実に」の線引き（#323で確定）

- 判定軸は「外部要因で変わる結果を約束しているか」。約束していれば緩和、していなければ維持する。
- 緩和する例: 効果や実現そのものの約束（断熱改修の効果は確実に出ます／確実に省エネを実現し／早く確実に前に進みます）。
- 維持する例: ①算術的必然（総額÷使用量に基本料金が含まれる以上「実質単価には確実に効く」）②コントロール可能性の記述（市場価格と対比した「基本料金は自社の運用で確実に効かせられる領域」）③動作・手続きの実務指示（確実にOFFにする／確実に引き継ぐ）④否定形（確実に採択されるわけではありません）⑤悪質勧誘の例示（高利回りで確実に儲かる）。
- 実測: src全体124件のうち緩和は3件、維持121件。大半はQUALITY_RULESが既に例外としているもの。

## 和暦→西暦の換算（#323で確立）

- 令和N年 = 2018 + N（令和元年=2019）。西暦を併記するときは必ずこの式で機械照合する。
- 検証プロンプトや発注文に換算表を書く場合、その表自体を機械照合の対象にする（#323では検証プロンプト側の換算表が誤っており、指示側の誤りが検証基準に混入した）。
- 制度の適用期間・締切の西暦併記を誤ると、読者が残存期間を数年単位で誤認する実害がある。

## バッチ生成の設計則（#323で確立）

- H2見出しの重複度は事後修正でなく生成指示の段階で解決する（見出しに固有文脈を織り込む指示を最初から入れる）。#322は初回Dice66.7%→事後修正33.3%、#323は指示段階で0.0%。
- 共通軸（複数ページに展開する前提条件）は、展開前に各ページのDATA_ACTUAL本体との照合を親が実施し、根拠のある対象にのみ配分する（#322の越境を#323は設計で防止）。
- 並列生成は利用上限に注意し、4-5並列程度に抑える。上限到達は最終出力の返却時に起きうるが、成果物のファイルは書き込み済みの場合があるため、失敗時はまず成果物の有無を確認してから再実行を判断する。

## 是正前に「配信されているか」を確認する（#326で確立）

- ソースを直しても読者に届かない場合がある。是正の対象ファイルが実際に公開画面へ配信されているかを、着手前または報告時に確認する。
- 確認すべき経路: ①コンポーネントがどこからもimportされていない（#325のCat6to20MoreCalculators.tsx・14 exportすべて未参照）②ページがリダイレクトで到達不能（#326のdemand-power-glossaryはnext.configの308でelectricity-glossaryへ転送）③ビルド対象外。
- 影響範囲を報告するときは「ソース上の件数」と「読者に届いていた件数」を区別する（#325は「2つの計算機が食い違う」と報告したが、実際に誤った金額が表示されていたのは1件のみだった）。

## 数値の誤りは3層で探す（#325・#326で確立）

- 第1層=文章の数値（FAQ・本文・表）。第2層=構造化データ（FAQPage/ArticleJsonLd等。検索結果に直接出るため実害が大きい）。第3層=実装（計算機・コンポーネント。読者が入力して得る結果が誤る）。
- 文章の誤りを見つけたら、同じ主題の構造化データと実装まで追う。#325はFAQの記述誤りから始まり、#326で計算機の実装誤り（*0.0085→*0.01）に到達した。
- 実装の是正では、丸めの順序（単価を丸めてから乗じるか、積を丸めるか）を画面上の検算と一致させる。

## 族の抽出は「率」だけでなく「型」で洗う（#326で確立）

- 同一主題の誤りは複数の型を持つ。#326の力率割引では ①率の誤り（0.5%・0.85%）②基準値の誤り（90%→85%）③係数と対応値の誤り（0.97は力率88%であって97%ではない）④増減方向の誤り（力率改善は係数を下げるのに「上げる」と記述）⑤条件の欠落（無条件の「▲15%」）の5型が併存していた。
- 抽出は文単位でなく行単位で行う（文分割は「通常90%を基準に」のように主語が前文にある記述を落とす）。さらに主題語（力率・割引・割増）を含まない記述（「力率改善で基本料金▲15%」）も拾えるよう、数値パターン側からも走査する。#326は抽出を3回作り直して3件→5件→8件に到達した。

## 現状判定はHEAD blobとの直接照合で行う（#327のF取り違えとCRLF汚染637件で確立）

- 発注の前提に書く「現状」は、作業ツリーの実測やgit statusの表示ではなく、HEAD blob（git show HEAD:<file>）の実測で確認する。作業ツリーの実測をHEADと取り違えると、存在しない作業（例:「内容不変のLF正規化コミット」）を発注してしまう。
- git statusのクリーン表示・git diffやcheckoutの沈黙を信用しない。index stat cacheが作業ツリー側のstat（サイズ・mtime）で汚染されていると、worktreeがHEADと異なっていてもgitは「変更なし」と判断し、status/diff/checkoutのすべてが沈黙する（実例: tracked 637件のCRLF化が数か月隠蔽されていた）。
- 判定は git hash-object <worktreeファイル> と git rev-parse HEAD:<path> の直接比較で行う。不一致なのにcheckoutが効かない場合は、rm → git checkout -- でindex blobから再展開する。
- 未コミットの内容差を見つけたら機械的に破棄しない。実在の履歴かを裏づけ（言及するコミット・PRの実在照合）してから救出/破棄を判定する（7/17議事録17行は066e4fbの実在照合のうえ救出）。
- EOL規律の運用: 復元・編集後は「HEAD blobがCRLFのファイルはCRLFのまま」まで確認する（月次page.tsx 4件）。

## 一括リンク改修・生成ファイルの検証（#328で確立）

- 構造ブロック（オブジェクト・グループ定義）の削除は正規表現で行わない。lazyマッチはブロックを跨いで無関係な定義を巻き込む（#328で4グループ72行の誤削除を差分検査で捕捉）。行ベースのブロックパーサで削除し、結果を手計算の期待値と照合する。
- 1行に複数要素が詰まったpacked行を編集したときは、対象外要素の巻き込み有無を「変更前後の対象外要素の多重集合比較＝差ゼロ」で機械確認する。目視や対象要素だけの確認では巻き込みを検出できない。
- 生成ファイル（articleSlugs.ts等）を手で触る前に再生成diffを確認する。diffが期待変更のみにならない場合は生成元がstaleである兆候（#328で383件の計測漏れ候補を発見）。staleの混入を避けるため、当該PRでは期待変更のみを手動適用し、再生成は独立したPRに分離する。
- アンカー着地カードの表記標準: title=着地ページH1の逐語・description=「〈節名〉」の節で確認できます。（節名は着地見出しの逐語）。同一着地への表記はサイト全体で統一する。

## 検出器は「検出器自身が効くこと」まで試験する（#333で確立）
- 欠陥の再発を防ぐ回帰テストを書いたら、その検査が実際に落ちることを確認する。欠陥を一時的に戻して赤くなるまでを1セットとする（#333では静的走査が直接経路のみを捕らえ、ヘルパ関数のreturn経由という間接経路を素通りしていた。ランタイム検査を足して両経路で落ちることを確認した）。
- 走査器の判定ロジック自体をテスト対象にする。#333の走査器はショートハンドプロパティ `{ source, ... }` を取りこぼしており、対象3件のうち2件が抽出漏れになっていた。`topLevelKeys(" source, cta_from: source ")` がsourceを含むことを検査する1本で、走査器の欠陥が可視化される。
- toMatchObject は余分なキーの存在を失敗にしない。「あるキーが無いこと」を保証したい場合はキー集合の完全一致（Object.keys(...).sort() の比較）で書く。#333以前はこの誤用により、GA4予約語の混入が5か月間テストを通り続けていた。
- GA4のイベントパラメータに campaign/source/medium/term/content を使わない（GA4のキャンペーン次元を上書きし、セッションの流入元帰属を破壊する。#333で409セッション・全体の2.9%がUnassigned化していたことが判明）。用途がある場合は cta_source のように接頭辞を付ける。
- 「欠陥を一時的に戻して赤くなるまで」を行うとき、対象ファイルに未コミットの変更があるなら git checkout -- で戻してはいけない（未コミット変更ごとHEADに戻る。#334で発生・blob hash照合で即検知）。変更内容を別名で退避（cp または git stash -- <file>）してから欠陥を再現し、確認後に退避から書き戻す。または先にコミットしてblobを固定してから行う。

## 副作用のあるスクリプトは「確認目的」でも実行しない（#333で確立）
- scripts/fetch-topline.mjs は import しただけでGSC/GA4を叩き4ファイルを書き出す（うち1件はtracked）。構文確認・依存確認の目的であっても import / 実行しない。静的に読むこと。
- 点検や動作確認を発注する側も、対象スクリプトの副作用（書き出し先・tracked有無）を確認したうえで指示を出す（2026-08-30のドライラン指示で「ファイル変更なし」と書いた発注ミスが先行事例）。
